# lngnb

**軽量でシンプルな、インターネット上の分散図書館・知識基盤。**

lngnbは、資料を保存し、見つけ、読み、引用し、改訂履歴を辿り、必要な資料を別の場所へ引き継ぐためのシステムです。個人や団体が独立して運営でき、一台でも利用できます。中央アカウントや、他のサーバーへの常時接続は必要としません。

## 現在の状態

Record形式・ID・署名の局所検査、Record・本文Blobの保存基盤、親履歴・本文宣言の管理用評価、暗号化鍵ファイルと端末からの秘密入力を実装した開発初期段階です。ヘルプ・版表示・設定候補の表示に加え、Linuxで鍵の作成・読込み確認・パスフレーズ更新を実行できます。初期化済みの正常な領域への新規資料・改訂・派生作成CLIを追加しています。保存領域の明示初期化と管理用状態診断も実行できます。完全固定指定で保存版の親・由来の宣言を確認できます。明示したローカル保存範囲の全版・親子宣言・由来と同世代の管理用診断を一覧表示でき、手動待ちの領域では根拠復旧の確認記録も行えます。公開リレー起動などは未実装で、工程③の対象試験は実行済みですが、G1〜G5全体は未合格です。

**仕様書・実装計画書の v1.0.0 は文書の版です。** ソフトウェアの開発版は `0.1.0-dev` で、初期版完成やリリースを意味しません。

## 開発用のビルドと確認

管理IPCの内部通信境界も実装中です。設定変更専用socketを`admin serve`と明示的な稼働中変更CLIへ接続しています。保存領域の排他を保持する所有者専用Unix socket、接続UIDの所有者/root照合、サイズ・時間制限を用意しています。完成署名Record一件の局所検査・保存を、停止中の資料作成CLIと共通の処理へ接続しました。保存確定後の応答失敗も区別します。完成Record一件を送る`record submit`を追加しました。接続先だけを確かめる`admin probe`も追加しました。前面の管理受理側は`admin serve`で起動・終了できます。4項目の明示設定保存と起動時の読込みを追加していますが、全管理状態のIPC診断や公開リレー起動・停止の製品CLIは未実装です。既存socket名は自動削除・再利用しません。

現在のビルド確認対象はLinux x86_64（Ubuntu 24.04）です。RustupとCリンカー（Ubuntuでは`build-essential`）を用意し、取得したリポジトリ内で実行します。Rust 1.85.0・edition 2024を採用し、ツールチェーンと構成を固定しています。依存版はCargo.tomlとCargo.lockで固定しています。初回の依存取得にはネット接続が必要です。独立照合試験にはPython 3.12とvenvを用います（Ubuntuでは`python3-venv`）。取得後のRustビルド・試験はofflineで実行します。

```sh
git clone https://github.com/nkkmd/lngnb.git
cd lngnb
rustup toolchain install 1.85.0 --profile minimal --component rustfmt --component clippy
cargo fetch --locked
python3 -m venv /tmp/lngnb-reference
/tmp/lngnb-reference/bin/pip install -r tests/requirements.txt
export LNGNB_REFERENCE_PYTHON=/tmp/lngnb-reference/bin/python
cargo fmt --all -- --check
cargo clippy --locked --offline --all-targets -- -D warnings
cargo test --locked --offline --all-targets
cargo build --locked --offline --release
./target/release/lngnb --help
./target/release/lngnb --version
./target/release/lngnb config show
./target/release/lngnb config show --data-dir /path/to/data
```

`config show`は未保存・未適用の設定候補を表示します。既定のデータ領域候補はカレントディレクトリの`./lngnb-data`で、指定したパスの読込み・作成、設定保存、ネットワーク接続は行いません。既存リレーの状態確認や初期化コマンドではありません。未対応操作・不正引数は終了コード2、出力失敗は1となり、成功とは表示しません。

鍵操作は、リポジトリ外に用意した所有者専用0700ディレクトリを明示します。自動作成・権限修正は行いません。前面の制御端末でパスフレーズを非表示入力し、作成・更新時は二度入力します。

```sh
./target/release/lngnb key create --key-dir /path/to/private-keys --name publisher
./target/release/lngnb key check --key-dir /path/to/private-keys --name publisher
./target/release/lngnb key change-passphrase --key-dir /path/to/private-keys --name publisher
./target/release/lngnb key recovery-status --key-dir /path/to/private-keys
./target/release/lngnb key check-residue --key-dir /path/to/private-keys --residue NAME_FROM_RECOVERY_STATUS
./target/release/lngnb key preserve-residue --key-dir /path/to/private-keys --residue NAME_FROM_RECOVERY_STATUS --backup-dir /path/to/private-backup --backup-name saved.key
./target/release/lngnb key restore-residue --key-dir /path/to/private-keys --residue NAME_FROM_RECOVERY_STATUS --restore-name restored.key --expect-key-id EXPECTED_KEY_ID
```

暗号化鍵ファイルを安全な別の場所にも保管し、パスフレーズは鍵とは別に保全してください。紛失は管理トークンで回復できません。複数資料で鍵を共用すると漏洩時の影響が広がります。鍵の紛失・漏洩・計画交代では新鍵と新Knowledgeへ移行し、同じKnowledgeの発行鍵は変更できません。`check`は現在名の復号・公開鍵一致の確認だけで、残存ファイルの復旧や過去の更新結果の確定ではありません。

残存物は、端末不要の`recovery-status`で名前と上限付き読取り結果を診断できます。読取り完了は形式・認証の成功ではなく、生成形式に合わない予約名は件数だけを示します。`check-residue`には一覧に出た生成形式名を明示し、その暗号文のパスフレーズを端末入力します。認証復号できた鍵IDだけを表示し、元の対象名・新旧・更新確定・削除可否は推測しません。どちらも書換え・採用・削除をせず、終了0は診断処理の終了だけです。

`preserve-residue`は、指定した残存暗号文を認証して、別の既存0700ディレクトリの新しい通常名へ同じ暗号文を保全します。保全元の現在名・残存物は残し、保全先の既存ファイルも上書きしません。保全先でもその暗号文のパスフレーズが必要です。過去の更新確定や新旧判定・残存物の整理許可にはならず、保全元の変更停止も解除しません。保全先の永続化確認後に元の暗号文の最終照合等ができなかった場合は終了5となり、両領域の全ファイルを保持して確認します。

`restore-residue`は、選択した残存暗号文を期待鍵IDと照合し、同じ領域の空いている通常名へ同じ暗号文を復元します。期待鍵IDは作成時の控え等と照合して明示してください。元名・新旧を推測せず、既存鍵は置換しません。全残存物と変更停止を維持し、成功しても過去の更新完了や残存物の整理許可にはなりません。復元先の永続化確認後に残存元の最終照合等が未完了・不一致なら終了6となり、全ファイルを保持して確認します。

元領域を保持したまま鍵操作を続けるには、控え等の期待鍵IDと選択した残存鍵を照合し、残存物のない別の専用領域へ`preserve-residue`で保全します。終了0を確認し、保全先を`key check`で認証して同じ鍵IDを照合した後、以降の`--key-dir`にその領域を明示します。元領域の変更停止は解除しません。コピー先のパスフレーズを変更しても、元領域の暗号文は旧パスフレーズで復号可能なままであり、鍵の失効・漏洩回復にはなりません。確認項目と失敗時の境界は[実装計画書§5.37](docs/implementation-plan.md)に示します。

鍵操作の終了コードは成功0、引数不正2、入力取消し130、保存未確定3、新鍵の永続化確認済みで旧暗号文の整理が不確実な場合4、保全先保存済みで最終照合等が未完了の場合5、復元先保存済みで最終照合等が未完了の場合6、その他の失敗1です。3/4/5/6や残存ファイルの通知では現在名・回復用暗号文を保全し、変更を繰り返さず確認してください。残存ファイルは自動採用・削除せず、既存鍵の置換・残存物の整理は未実装です。結果出力の失敗は保存の失敗と同じではなく、鍵操作完了後の出力失敗は診断で区別します。SIGKILL/SIGSTOP・端末消失等の復元は保証しません。端末復元失敗時は入力を続けず別の正常な端末を使用し、必要なら元端末で`stty sane`を使います（元設定の完全復元ではありません）。

保存領域の初期化と状態診断は、対象を明示します。

```sh
./target/release/lngnb data init --data-dir /path/to/new-data
./target/release/lngnb data status --data-dir /path/to/existing-data
```

`data init`は既存の親ディレクトリの下へ所有者専用0700の新しい保存領域を作ります。既存領域は空でも拒否し、上書き・自動移行・再初期化しません。今回の初期化はローカル保存だけで、待受先・投稿モード等の設定保存やリレー起動は未実装です。終了3では初期化の完了を確認できず、作成済み・途中の領域が残る可能性があります。保全して確認し、削除や再初期化を繰り返さないでください。初期化後の出力失敗は終了1で区別し、状態診断の成功だけを初期化失敗からの復旧完了とは扱いません。

`data status`は同じ排他を保持して、起動状態、診断対象の内部世代（`diagnostic_generation`）、Recordの管理用再検査件数、本文状態、保持実体の欠損・破損・孤立・途中ファイル、空き容量を表示します。保存層の共通診断で親不足と本文不足を区別し、診断結果を保存済み評価へ書き戻さず、正常停止印・公開資格を付与しません。保持本文の欠損等を新たに検出すると、既存APIが停止印と履歴を記録します。欠損ファイルを戻しただけでも手動確認待ちは解除しません。正常領域・既に手動待ちの領域への診断だけでは、その論理状態を変更しません。未対応・破損・lock競合・予算不足等では終了1とし、途中件数を成功として表示しません。この停止中診断の予算調整、同期・pin・公開等の製品全状態表示は未実装です。ローカル保存の明示再開には別操作の`data resume-local`を使います。稼働中管理受理側の診断には別操作の`admin status/evaluate`を使い、自動では切り替えません。診断処理の終了0は、資料や保存領域全体の正常・公開可能・復旧完了を意味しません。

稼働中の管理受理側の設定は、停止中の`config-save`とは別操作で変更します。

```sh
./target/release/lngnb admin config-change --data-dir /path/to/existing-data --request-timeout-ms 5000 --max-new-records 100 --max-diagnostic-records 1000 --startup-records-per-step 100
```

4項目すべてを明示し、値域は`config-save`と同じです。専用`admin-config.sock`で認証・値照合を行い、同じ排他・writerで設定・世代・旧新履歴を原子的に保存した後、通信期限・session新規件数上限・診断件数を次操作へ反映します。起動分割件数は次回起動用です。消費済み件数を下回る上限は拒否し、counter・byte上限・非保存の起動/SQL/診断時間予算は変更しません。今回の要求・応答には変更前の通信期限を使います。

送信前の接続・認証失敗は終了1、送信開始後の通信失敗・不正/不一致応答は終了3「確定不明」、保存・適用確認後の出力失敗は終了1で区別します。終了3や中断では保存済みの可能性があります。領域とsocketを保全して確認し、自動再送・直接DB保存・旧endpointへの代替接続・残存物削除はしません。受理側は不正通信・保存失敗・応答喪失で正常停止を禁止します。成功も正常停止・全資料検査・公開・復旧完了ではなく、手動待ちは解除しません。`config-save`は稼働中に自動でこの経路へ切り替えません。

停止中の領域に保存された管理設定だけを確認できます。

```sh
./target/release/lngnb admin config-show --data-dir /path/to/existing-data
```

同じ排他の下でread-only SQLite接続と読取りtransactionを使い、保存形式・設定値・履歴を照合して4項目を表示します。未保存は`saved: false`とし、既定値で埋めません。表示は保存値であり、現在の適用値・次回起動の成功・全資料の健全性ではありません。`config show`は従来どおり領域を読まない設定候補表示です。

設定・世代・履歴・起動検査cursor・起動印・手動確認待ちは更新しません。整合した手動待ち領域でも読めますが、稼働中の排他競合・不正設定・履歴不一致・欠損・旧保存版・不正権限は終了1で拒否します。修復・補完・初期化・起動・IPC接続・socket整理へ切り替えません。結果出力失敗も終了1です。SQLiteのWAL/SHM補助ファイルのI/Oはあり得るため、領域内の全ファイルが不変という保証ではありません。不正/重複/余分な引数は領域接触前に終了2です。

停止中の正常な領域へ、管理受理側4項目を明示保存できます。

```sh
./target/release/lngnb admin config-save --data-dir /path/to/existing-data --request-timeout-ms 5000 --max-new-records 100 --max-diagnostic-records 500 --startup-records-per-step 100
```

4項目すべてが必須で、省略値の補完や既存値との部分更新はしません。値域・ASCII表記は`admin serve`と同じで、不正/重複/不足引数は領域に触れる前に終了2です。同じ排他の下で既定予算による全起動検査・管理用評価を完了してから、設定/世代/旧新履歴を同じDBへ保存し、最後にローカルsessionの正常停止を記録します。指定値は今回の検査予算を変更せず、この保存操作で起動・適用はしません。次の`admin serve`で読み込みます。`config show`は未保存・未適用の候補表示のままです。

稼働中の排他競合・手動確認待ち・不正な保存値・検査未完了・保存失敗では成功にせず、終了3として領域を保全します。正常終了を確認できない場合は旧値または新値の保存済み/未確定の可能性があり、再保存・再初期化を繰り返さず確認してください。IPCへ代替接続せず、領域/DB/socketの作成・削除、既存設定の自動補完や手動待ち解除もしません。正常な領域の起動検査記録は更新されます。設定保存と正常停止の確認後に結果出力だけが失敗した場合は終了1です。途中のSIGKILL等は通常のsignal終了となり、専用終了コードの通知は保証しません。公開許可・復旧確認・リレー起動の操作ではありません。

管理受理側だけを前面で起動できます。公開HTTPや秘密鍵の処理は行いません。

```sh
./target/release/lngnb admin serve --data-dir /path/to/existing-data
```

既存の正常停止領域を明示します。同じ排他のまま分割起動検査・保存Record/Blob照合・管理用親評価を完了してからsocketを開きます。起動中も一般配信はありません。手動確認待ち・未完了検査・予算不足・既存socket名を成功にせず、socketの自動採用・削除、初期化、復旧解除はしません。段階ごとの予算は次のoptionで指定できます。Record検査の分割件数は次のoptionで指定できます。

この起動の受理側予算を明示できます。

```sh
./target/release/lngnb admin serve --data-dir /path/to/existing-data --request-timeout-ms 5000 --max-new-records 100 --max-diagnostic-records 500 --startup-records-per-step 100
```

`--request-timeout-ms`は受信・応答それぞれの通信期限（1〜30,000 ms、既定30,000）、`--max-new-records`は一回の起動で新規挿入するRecord数（1〜10,000件、既定10,000）です。現CLIでは既定上限の引下げだけを認めます。後者は既存の同一Recordの重複送信を数えず、保存済み総件数や起動検査件数の上限を変更しません。通信期限は保存syscallを強制中断せず、受付待ち100 msや送信側`record submit`全体の30秒予算も変更しません。

`--max-diagnostic-records`は`admin evaluate`一回の全件評価に使うRecord数予算（1〜10,000件、既定10,000）です。この起動だけで既定上限の引下げを認め、適用値を`max_diagnostic_records`として起動時に表示します。起動検査・保存受付・`admin status`の実行時情報・Blob走査やbytes/辺/時間予算は変更しません。既存IPCの固定応答へ設定項目を追加せず、この診断clientから受理側設定を変更することもありません。対象が予算を超えれば部分件数を返さず、client終了1・受理側終了3で保全停止します。値の変更や省略で手動確認待ちは解除されません。

`--startup-records-per-step`は起動時のRecord局所検査と依存入力収集で、一回のstepが扱う件数（1〜10,000件、既定10,000）を指定します。小さい値では同じ排他と永続cursorのまま複数stepへ分け、検査対象全体を終えるまで受付socketと起動完了表示を出しません。総Record数の上限や検査省略数ではなく、段階ごとのbytes/辺/時間・Blob検査・親評価予算も変更しません。保存受付や稼働中の評価診断予算とも別です。適用値は`startup_records_per_step`として起動完了時に表示し、この起動の検査へ適用します。途中の破損・失敗・取消しでは正常停止にせず、値を変えても手動待ちは解除しません。

`--startup-record-bytes-per-step`は、Record局所検査と依存入力収集の各stepで扱うRecordのbyte予算（1〜67,108,864 bytes、既定64 MiB）です。件数予算と併用し、どちらかに達した正常なstep境界では同じ排他/cursorで次stepへ進みます。検査対象の総byte数やRecord形式の上限、Blob検査・辺・時間・SQL予算は変更しません。単一Recordも収まらなければ検査を飛ばさず、socket/起動完了表示前に終了3で保全停止します。小さい処理予算の不足は署名不正ではなく、設定変更や次回の省略でも手動待ちは解除しません。

このRecord byte予算は起動引数専用で、`admin config-save/config-show`の保存対象4項目へは追加しません。省略時は64 MiBへ戻り、起動完了時に`startup_record_bytes_per_step`を表示します。`config-save/probe/status/evaluate/config-show`への指定は領域接触前に終了2です。

`--startup-blob-bytes-per-step`は、物理Blob検査と本文評価入力の各stepで全体hashを確認するbyte予算（1〜67,108,864 bytes、既定64 MiB）です。Blob間のstep境界で分割し、同じ排他と既存の検査台帳で全対象を終えるまでsocket/起動完了を出しません。一つのBlob内部を途中まで検査して完了にせず、一件も収まらなければ終了3で保全停止します。保持本文の欠損・破損を検出した場合も正常起動にせず、既存ファイルを採用・削除・修復しません。

このBlob byte予算も起動引数専用で、保存対象4項目には追加しません。省略時は64 MiBへ戻り、適用値を`startup_blob_bytes_per_step`として起動完了時に表示します。Record・Blob件数/対象数・辺・時間・SQL・全体量・受付/診断予算は変更せず、不足や破損後の設定変更・省略で手動待ちを解除しません。`config-save/probe/status/evaluate/config-show`への指定は領域接触前に終了2です。

`--startup-blob-targets-per-step`は、物理Blob検査の一覧項目数と本文評価入力の対象数を、それぞれのstepで1〜10,000（既定10,000）に指定します。物理検査ではBlob・途中ファイル・欠損等の一覧項目を数え、本文評価では未保持・失敗観測だけのBlobも一対象として数えます。hashするbytesが0でも対象数には計上します。段階間で件数が同じとは限らず、全資料のBlob総数の上限や検査省略数ではありません。

byte予算と併用して同じ排他/台帳で全対象を検査し、全段階完了後だけ`startup_blob_targets_per_step`を表示します。起動引数専用で保存4項目へ追加せず、正常再起動で省略すれば10,000へ戻ります。Record・byte・辺・時間・SQL・全体量・受付/診断予算は変えず、設定変更・省略で手動待ちを解除しません。他の管理操作への指定は接触前に終了2です。

`--startup-record-edges-per-step`は、依存入力収集の各stepが扱うRevisionの親参照数（1〜100,000、既定100,000）です。既存のRecord件数/byte予算と併用し、正常な境界で同じ排他/cursorを使って次stepへ進みます。総辺数や親参照の規範上限を変えず、親評価そのもののstep、Blob・時間・SQL・受付/診断予算も変えません。一つのRevisionの親参照数も収まらなければ省略せず、終了3で未受付の保全停止とし、署名不正や規範違反にはしません。

起動引数専用で、保存4項目には追加しません。全段階完了後だけ適用値を`startup_record_edges_per_step`として表示し、正常再起動の省略時は100,000へ戻ります。失敗後の設定変更・省略で手動待ちは解除しません。他の管理操作への指定は領域接触前に終了2です。

`--startup-evaluation-records-per-step`は、親評価の各stepで新たに判定するRecord数（1〜32、既定32）です。Genesisや、依存不足でpendingとなるRecordも処理件数に含めます。入力収集の`--startup-records-per-step`とは別で、親評価の全対象数・検証規則・入力収集・台帳/cache照合・依存順序構築・時間・SQL予算は変えません。下準備全体の処理量をこの件数で制限するものではありません。

同じ排他/評価台帳で全対象の判定処理が終わるまでsocket/起動完了を出しません。全件を処理しても、依存不足解消・全件valid・公開許可・復旧完了を意味しません。保存失敗では途中結果を成功表示せず、最後の確定checkpointと一次データを保全して正常停止にしません。保存対象外の起動引数で、正常再起動の省略時は32へ戻り、適用値を`startup_evaluation_records_per_step`として表示します。失敗後の変更・省略は手動待ちを解除せず、他の管理操作への指定は接触前に終了2です。

`--startup-inspection-timeout-ms`は、Record局所検査と物理Blob検査で共有する各stepの時間予算（1〜60,000 ms、既定60,000）です。件数/byte予算と併用し、既存の安全な境界で分割します。起動全体の制限時間ではなく、OSのI/O待ち、一件の署名/hash検査、checkpoint保存を強制中断する実時間保証ではありません。このstep内のSQL照合は、既存どおりSQL予算とstep残時間の短い方を使います。

同じ排他/永続cursorのまま必要な全検査を完了してから受付し、適用値を`startup_inspection_timeout_ms`として表示します。一件も進められない予算不足等では検査を飛ばさず終了3で保全停止し、署名不正とは呼びません。正常な未完了stepだけを続け、失敗後に既定値で自動再試行しません。設定変更・省略で手動待ちは解除しません。

この値は起動引数専用で保存4項目に追加せず、正常再起動の省略時は60,000へ戻ります。依存入力収集/本文評価入力/親評価の時間予算、保存session全体で使うSQL予算、受付/診断/通信の予算は変更しません。他の管理操作への指定は領域接触前に終了2です。

`--startup-record-input-timeout-ms`は、依存入力収集の各stepの時間予算（1〜60,000 ms、既定60,000）です。`EvaluationInputBudget.elapsed`へ渡し、`EvaluationLimits.elapsed`との短い方を使います。保存済みcache/一次Recordのprefix照合、新規Recordの局所検査・依存情報収集、checkpoint保存前の期限確認を含みます。期限不足は当該stepを成功にせず、以前の確定cursorを保全して終了3で停止します。件数/byte/辺数による正常な未完了stepだけを継続します。

起動全体の累積期限、本文評価入力・親評価（依存順序構築を含む）の時間予算ではありません。段階前後の共通file状態照合や、OSのI/O待ち・一件の署名検査・checkpoint保存を強制中断する実時間保証も追加しません。保存sessionのSQL予算・handler scopeは変えず、新しいSQL監視は追加しません。保存4項目・候補表示・稼働中診断/受付予算は不変です。全検査/socket準備後に`startup_record_input_timeout_ms`を表示し、正常再起動の省略時は60,000へ戻ります。他操作/不正/重複指定は接触前終了2、失敗後の変更/省略では手動待ちを解除しません。

`--startup-blob-input-timeout-ms`は、本文評価入力の各stepの時間予算（1〜60,000 ms、既定60,000）です。`EvaluationBlobBudget.elapsed`へ渡し、`EvaluationLimits.elapsed`との短い方を使います。収集済みRecord入力・既知根拠・保存済み本文検査台帳の照合、参照一覧生成/stat確認、新しい対象の全体hash検査、保存前の根拠/実体照合を含みます。時間予算はhashだけの期限ではなく、対象数/byte予算による正常な未完了stepだけを同じ排他と台帳で継続します。期限不足では以前の確定進捗を保全し、受付前に終了3で停止します。

物理Blob起動検査や親評価（依存順序構築を含む）、起動全体の累積期限ではありません。段階前後の共通file状態照合やOS I/O・一Blobのhash・保存を強制中断する実時間保証、SQL監視/handler追加はありません。保存4項目・他予算・候補表示は維持します。全検査/socket準備後に`startup_blob_input_timeout_ms`を表示し、正常再起動の省略時は60,000へ戻ります。他操作/不正/重複指定は接触前終了2、失敗後の変更/省略で手動待ちを解除しません。

`--startup-evaluation-timeout-ms`は、親評価の各stepの時間予算（1〜60,000 ms、既定60,000）です。保存済み評価台帳・入力cacheの照合、依存順序構築、新しいRecord判定、結果符号化・保存前の根拠照合を含み、新規判定だけの期限ではありません。起動の親評価段階だけで`EvaluationLimits.elapsed`との短い方を使い、局所/物理検査・依存入力・本文評価入力、保存sessionのSQL予算、稼働中診断/受付予算は変更しません。

件数による正常な未完了stepは同じ排他/台帳で続けます。期限不足は受付前に終了3で保全停止し、以前の確定checkpointと一次データを維持します。起動全体の累積期限や、段階前後の共通file状態照合・OS I/O・一件の判定・保存を強制中断する実時間保証ではありません。新しいSQL監視/handlerや保存対象は追加しません。全検査/socket準備後に`startup_evaluation_timeout_ms`を表示し、正常再起動の省略時は60,000へ戻ります。不正/重複/他操作指定は接触前終了2、設定変更/省略で手動待ちは解除しません。

`--sql-inspection-callbacks`は、既存のSQL読取り照合群ごとの進捗callback上限（1〜100,000、既定100,000）です。SQLiteが概ね1,000 VM命令ごとに呼ぶcallbackを数えます。正確な命令数・行数・実時間の上限ではなく、短いSQLではcallbackが来ない場合もあります。全SQLを監視する設定ではなく、保存・commit・rollbackへ中断handlerを追加しません。このcallback指定ではSQL時間予算やOSのI/O待ち、Record/Blob/親評価等の処理予算は変えません。

設定読込み前から同じ排他/接続の保存sessionへ適用し、起動後の受理・診断・終了処理内の既存SQL照合群にも使います。起動専用ではありません。全起動検査とsocket準備後に`sql_inspection_callbacks`を表示します。保存対象4項目へ追加せず、正常再起動の省略時は既定へ戻ります。他の管理操作への指定は接触前終了2です。

`--sql-inspection-timeout-ms`は、同じSQL読取り照合群ごとの時間予算（1〜60,000 ms、既定60,000）です。設定読込み前から同じ保存sessionへ渡し、起動後の既存照合群にも使います。callback上限と併用し、親ジョブの残り時間がある照合では既存どおりその残り時間以下に制限します。進捗通知時と照合群の前後で期限を確認しますが、OSのI/O待ちを強制中断する実時間保証ではなく、全SQL・保存・commit・rollbackへの監視も追加しません。

全起動検査/socket準備後だけ`sql_inspection_timeout_ms`を表示します。保存対象4項目へ追加せず、正常再起動の省略時は60,000へ戻ります。Record/Blob/親評価の時間予算、通信期限、callback数や件数/byte予算は変えません。他の管理操作への指定は接触前終了2です。予算不足・設定変更・省略は既存手動待ちを解除しません。

SQL予算超過は破損・署名不正とはせず、受付/成功表示を止める既存の失敗経路を使います。先行running印より前のread-only照合で拒否された場合はDBと元の起動状態を維持します。稼働開始・変更開始後の失敗では正常停止を記録せず、手動待ちを保全します。設定変更・省略で既存の手動待ちは解除しません。予算超過後の自動再試行や既定値への切替もしません。

指定した予算の適用値をsocketの起動表示に続けて出力します。保存対象4項目は、項目ごとに起動引数→検査済み保存値→既定値の順で選びます。明示引数は自動保存せず、次回の省略時は保存値（未保存なら既定値）へ戻ります。不正な保存値・履歴不一致・読取り失敗は、明示引数や既定値で覆わず受付前に終了3です。同じ排他のまま設定読込みから全起動検査を行い、手動確認待ちは解除しません。既存の`config show`は候補表示のままです。ASCIIの先頭0なし正整数だけを受け付け、0・上限超過・重複指定・符号・空白・小数・不明optionは領域へ触る前に終了2で拒否します。これらのoptionは`admin probe/status/evaluate`には指定できません。通信期限切れや新規件数上限超過は既存の保全停止（終了3）となり、既に保存したRecordを削除せず、手動確認待ちを自動解除しません。値の変更や診断だけを復旧完了とは扱いません。

別の端末から`record submit`を実行できます。`admin probe`等の要求0bytesでの切断は無操作として扱います。最初のbyte以降の途中frame、不正Record、認証/保存/応答失敗では保守的に受理側を終了し、正常停止を記録しません。入力と領域、残っているsocketを保全して確認してください。一件の保存応答を受け取っても受理側全体の正常終了の証明ではありません。

前面端末のCtrl-C（SIGINT）または対象プロセスへのSIGTERMで終了を要求します。受付待ちは100 msごとに停止要求を確認し、既に処理中の一要求は終結させます。受信と応答の通信予算は既定では各30秒で、起動検査・保存syscallを即時中断する保証はありません。障害がなければ自分が作成した同一socketだけを閉じて整理・fsyncし、その後の最後の保存操作で正常停止を記録します。socket整理や正常停止commitの失敗は終了3であり、socket整理後に失敗するとsocketが残らない場合もあります。起動途中の取消し・不正通信・保存障害・応答喪失も終了3、signal設定失敗と正常停止後の結果出力失敗は終了1、引数不正は2です。signal設定前の中断やSIGKILL等は通常のsignal終了となり、正常終了やsocket整理は保証しません。常駐化、遠隔停止CLI、公開リレーは未実装です。ローカル保存の明示再開には別操作の`data resume-local`を使います。根拠復旧の確認記録は停止中の`data recovery-confirm`で行います。

設定4項目の共通保存と、保存成功後に受理側の実行時予算を変更する内部APIを追加しています。通信期限・新規Recordのsession全体上限・診断件数は次操作から、起動分割件数は次回起動に使います。保存済み件数を下回る設定は拒否し、counterはresetしません。失敗では適用を先行させず、正常停止を禁止します。この共通処理は専用管理IPCと`admin config-change`へ接続しています。既存`admin config-save`は停止中の保存だけを行い、その操作中の予算へ適用しません。

管理socketの接続先だけを診断できます。

```sh
./target/release/lngnb admin probe --data-dir /path/to/existing-data
```

`record submit`と同じ領域・socketの権限/所有者/同一性と接続先kernel UIDを、最大30秒の接続予算で照合し、要求bytesを送らず切断します。成功はその時点のOS接続診断だけです。相手が要求を受理できるか、lngnbのプロトコルに対応するか、保存領域が正常かは確認しません。公開可否・正常停止・復旧完了も判定しません。接続失敗・診断出力失敗は終了1、引数不正は2です。DB/lockを開かず、領域の作成・設定保存・socket削除・再送・直接保存への切替はしません。接続は相手のbacklogを一枠使い、相手には要求なしの切断として観測されます。手動確認待ちは解除しません。

稼働中の管理受理側の実行時情報は、専用socketから取得できます。

```sh
./target/release/lngnb admin status --data-dir /path/to/existing-data
```

`admin-status.sock`の所有者/0600/単一link/同一性と接続先kernel UID（領域所有者/root）を照合し、要求bytesを送らず固定長の診断応答を読みます。取得するのはローカル世代、この保存sessionの新規Record件数・保存bytes、対応する予算、受信/応答期限、空き容量・管理予約・警告だけです。新規件数は重複を除き、保存済み総件数ではありません。容量はその時点の試料で、以降の書込み成功を保証しません。Record/Blobの全量再検査、親不足や公開・pin・同期・履歴全体の診断は含みません。成功は診断応答の取得/照合だけで、資料保存・健全性・公開・正常停止・復旧完了の判定ではありません。

接続から応答まで一つの最大30秒予算で、未知版/長さ/不正値/途中応答を成功にしません。DB/lockを直接開かず、初期化・保存要求・再送・残存物整理・手動待ち解除もしません。失敗や診断出力失敗は終了1、引数不正は2です。旧受理側等で診断endpointがなければ失敗し、`admin.sock`へ代替接続して旧受理側を停止させることはありません。起動済みの同UID/root相手の意図的な偽装やfd譲渡は防御範囲外です。

`admin serve`はRecord用・実行時診断用のsocketも同じ排他の存続中だけ保持します。Record要求の処理中は診断も直列に待機するため、長い進行要求がある場合は診断期限に達することがあります。診断接続のUID/endpoint照合、診断読取り、応答に障害があれば受理側も保全停止して正常停止を記録しません。正常終了では自分が作成した同一socketを整理・fsyncした後にwriter.finishへ進みます。診断socketの既存名・差替え・削除/fsync失敗は成功にせず、異常終了後は残存物を保全します。整理途中の障害では一部の自分のsocketが既に除かれている場合もあります。

稼働中の保存・評価診断は別の操作で実行します。

```sh
./target/release/lngnb admin evaluate --data-dir /path/to/existing-data
```

`admin-evaluate.sock`だけへ接続し、所有者/0600/単一link/同一性とkernel UIDを照合した後、要求bytesを送らず固定応答を取得します。同じ排他を保持する受理側が、保持Blob・途中/孤立実体を再走査し、Recordの署名・親依存・参照本文を共通診断で再検査します。保存済み総Record数、valid/pending/invalidと本文verified/missing/unavailable、診断対象の内部世代を表示します。通常の本文未取得と親不足は診断結果として表示でき、署名不正・保存破損と混同しません。評価を永続確定せず、公開・pin・同期・重要履歴全体の診断、復旧確認・再開は行いません。

再走査は保存層の既定10,000実体/64 MiB、評価は最大`--max-diagnostic-records`件（省略時10,000件）・Record 64 MiB・100,000辺・参照本文64 MiBまでで、両処理の経過予算は5秒です。処理境界で期限を検査し、ファイル/DBのsyscallを途中で強制中断する保証はありません。応答通信には受理側の通信期限、接続から応答全体にはclientの30秒予算を適用します。これらは処理予算で、Record形式の規範上限ではありません。既存の`admin status`や`admin.sock`へ代替接続せず、停止中は失敗します。停止中の診断は`data status`を明示してください。

保持実体の欠損/破損/途中/孤立、予算超過、検査/認証/応答失敗では部分集計を返さず、受理側は正常終了を禁止して保全停止（終了3）します。検出結果を管理履歴へ確定したことは意味せず、稼働中印と残存socketを保持して停止中診断・所定の復旧確認へ進みます。clientは取得/照合/出力失敗を終了1、引数不正を2とし、保存要求・自動再送・DB直接読込み・socket削除・手動待ち解除は行いません。遅延やclient取消しでも保全停止する可能性があります。成功後も保存内容は変化し得るため、全資料の恒久的な健全性や公開資格の証明にはしません。

`admin serve`は評価socketも同じ排他の存続中だけ保持し、Record・実行時診断・評価診断を直列化します。正常終了では四つの自分のsocketを同一性確認して整理・fsyncした後、別操作のwriter.finishへ進みます。既存評価socket名・差替えは自動採用/削除せず、失敗時には全残存物を保全してください。

完成署名Record一件を、既に稼働している同じ領域の管理受理側へ送れます。

```sh
./target/release/lngnb record submit --data-dir /path/to/existing-data --record /path/to/record.cbor
```

入力は2 MiB以下の単一link通常fileで、親を含むsymlinkや特殊fileは拒否します。局所署名検査後、所有者専用の領域・0600 socketと接続先のkernel UID（領域所有者/root）を照合して送ります。最大30秒の通信予算で、受信応答の版・長さ・Record ID・挿入有無を確認します。接続前の失敗は終了1、送信開始後の失敗/不正応答は保守的に終了3（保存確定不明）、確定応答後の結果出力失敗は終了1です。成功は一件のローカルcommit応答だけで、親評価・本文保持・pin・公開・正常停止や復旧完了とは別です。入力と領域を保全し、応答がないまま再作成しないでください。プロセス中断等で結果を返せなかった場合も、既に保存済みの可能性があります。

この送信CLIは管理受理側を起動しません。別の端末で`admin serve`を起動して使用できます。製品リレーの起動CLI・全管理状態のIPC診断は未実装です。管理受理側4項目の保存設定は`admin serve`の起動時に検査・適用します。領域の自動作成、socket削除、自動再送、直接DB保存への切替はしません。秘密鍵・パスフレーズ・本文Blobは送りません。同UID/rootの意図的な差替えや認証後のfd譲渡は防御範囲外です。

新規資料は、schema 12・正常停止状態のデータ領域と、残存物のない鍵領域を明示して作成します。保存領域は次の`data init`で作成できます。資料作成そのものは領域の新規作成・復旧を行いません。期待鍵IDは事前の`key check`等の控えと照合してください。metadata入力は仕様書A2の項目を持つ決定的CBOR mapです。言語ラベルの小文字化・型の既定値補完は署名前に行い、衝突は拒否します。

```sh
./target/release/lngnb document create --data-dir /path/to/existing-data --key-dir /path/to/private-keys --name publisher --expect-key-id EXPECTED_KEY_ID --payload /path/to/body --metadata /path/to/metadata.cbor
```

本文の既定予算は16 MiB、`--max-payload-bytes N`で0〜67,108,863 bytesへ明示変更できます。metadata上限は262,144 bytesです。`--media-type type/subtype`を省略すると媒体未指定となり、内容や拡張子から推測しません。本文・Record全体のセッション予算と、既存領域の起動検査予算も別途必要です。現在のCLIで既存集合の起動予算は調整できず、超過時は成功にしません。

成功時はKnowledge/Genesis/Revision IDを表示します。本文→Genesis→Revisionは段階ごとに保存するため、終了3では一部または全部の保存済み・未確定の可能性を残します。全領域を保全し、再作成せず確認してください。保存・正常終了後の出力失敗は終了1で区別します。引数不正は2、入力取消しは130、その他の保存前失敗は1です。手動確認待ち・鍵残存物を自動解除せず、作成成功でもpin・公開許可を付けません。新規Recordの管理用評価はdirtyとなり、次回起動検査等で再評価します。

同じKnowledgeを改訂するには、完成CBORのGenesisと親Revisionを明示します。本文・metadata・媒体は毎回指定し、元版から自動継承しません。

```sh
./target/release/lngnb document revise --data-dir /path/to/existing-data --key-dir /path/to/private-keys --name publisher --expect-key-id EXPECTED_KEY_ID --genesis /path/to/genesis.cbor --parent /path/to/parent.cbor --payload /path/to/new-body --metadata /path/to/new-metadata.cbor
```

複数親は`--parent PATH`を繰り返し、最大256件です。親を自動選択せず、親なしの別初版を作る場合だけ`--no-parents`を明示します。両方の併用・指定省略・重複親は拒否します。指定Recordは各2 MiB以下、Genesisと親の入力合計は16 MiBまでです。これはCLIの処理予算であり、小さい予算への超過を署名不正とは扱いません。既存の安全な読取り・秘密端末・期待鍵ID照合・署名APIを共有します。

全起動検査後、同じ排他の下で指定Genesisと全親の保存を確認し、新しい本文→新Revision→正常停止の順で保存します。起点・親を自動取込みせず、保存先にない場合は新本文/Recordを保存せず終了3で保全停止します。稼働中IPCへ切り替えません。引数2・保存前失敗1・入力取消し130・保存未確定3・保存/正常停止後の出力失敗1は作成CLIと共通です。保存成功は全祖先の有効性・評価確定・pin・公開を保証せず、署名済みの元版・鍵・由来を変更しません。全保存版・分岐・由来の確認には`document history`を使います。

局所検査の成功は、親履歴の検査完了・pin採用・公開許可を意味しません。保存機能は内部基盤と接続済みCLIの試験対象であり、公開リレーを含む製品全体の適合を意味しません。Blobの起動時照合では、不完全・孤立・破損・欠損を確認待ちにし、自動削除や公開を行いません。保存RecordとBlobの起動検査は途中から再開でき、未完了の間は通常の書込みへ進めません。起動検査から親評価までを段階的につなぐ内部経路でも、全段階の処理終了前にwriterを返さず、開始時の手動確認待ちを維持します。

管理用の親評価では、Record入力の収集・署名検査、参照本文Blobのファイル単位のhash検査、既定32 Recordずつの判定を分割して再開できます。検査来歴と現在の入力を照合し、完了した入力検査を再利用します。参照一覧・依存情報全体の読込みと順序構築、最後の評価確定には、引き続き集合全体の予算が必要です。詳しい境界は[実装計画書の§5.12〜5.13](docs/implementation-plan.md)に示します。

収集完了・評価の処理終了・依存不足の解消は別々に判定します。不正根拠を再検査できない場合は保留とし、修復後も手動確認待ちを自動解除しません。根拠復旧の再検査と管理者確認を記録する内部機能を追加しています。その成功だけでは再開せず、別の明示操作と現在のデータ・再開台帳の検査を経て、ローカル保存の書込みだけを再開できます。一般配信の再開とは別です。結果はその世代の管理用診断であり、pin・公開資格を付与しません。根拠復旧の確認記録は`data recovery-confirm`、保存範囲の一覧は`document history`へ接続しています。ローカル保存の明示再開は`data resume-local`へ接続しています。同期通信は未実装です。

Blobの明示保持・本文参照・既知不正根拠に加え、期限付き内部仮保存の台帳と保護根拠の診断を追加しています。削除予定の記録・保持変更による取消しに加え、未参照・期限終了の本文を再検査して整理し、中断時に明示復旧する内部経路を追加しています。過去の約束と履歴は保全します。HTTP受付票・公開制御・バックアップとの整理結合は未実装です。

試作DBはschema 12のみ対応します。schema 1〜11を自動移行・再初期化せず、旧DBは保持したまま別の新規領域で試験します。

実行時データや秘密情報はリポジトリ外で管理してください。正式な保存保証・性能評価の対象条件は仕様書に従い、ビルド成功と区別します。WSL2等の対応は未判定です。

- 資料の登録・公開、検索・閲覧、固定版の引用、改訂履歴の参照

派生は元Knowledgeの改訂と分け、由来のGenesisとRevisionを組で明示します。

```sh
./target/release/lngnb document derive --data-dir /path/to/existing-data --key-dir /path/to/private-keys --name publisher --expect-key-id EXPECTED_KEY_ID --origin-genesis /path/to/source-genesis.cbor --origin-revision /path/to/source-revision.cbor --payload /path/to/derived-body --metadata /path/to/derived-metadata.cbor
```

`--origin-genesis`、`--origin-revision`の順の組を1〜128組指定します。各組の局所署名と種別・Knowledge・Genesis・発行鍵の直接対応を検査し、重複を拒否します。由来には三IDの完全固定参照を整列して入れ、新しいKnowledgeと親なし初版を派生先の明示鍵で署名します。元発行鍵と派生先鍵の一致、元版の保存先への取込み、元版の本文・全祖先の保持は要求しません。由来は承認や必須依存、自動取得の指示ではありません。

本文・metadata・鍵・保存・失敗保全は作成CLIと共通です。元Record群は各2 MiB・合計16 MiBを確保前に制限し、NOFOLLOW・単一link・属性前後照合・取消しを共有します。元本文・metadata・親・由来を暗黙継承せず、署名済み元Recordや鍵を変更しません。派生先でも保存成功と全祖先評価・pin・公開・復旧完了は別です。

保存版の署名に含まれる親・由来は、Knowledge・Genesis・Revisionの三IDをすべて明示して確認します。鍵や制御端末は不要です。

```sh
./target/release/lngnb document inspect --data-dir /path/to/existing-data --knowledge-id KNOWLEDGE_ID --genesis-id GENESIS_ID --revision-id REVISION_ID
```

同じ排他の下で既存の領域検査・予算と共通の固定版読取りを使い、指定と一致した版の三ID・署名鍵ID・親・由来の宣言を表示します。親のない初版や分岐を自動選択・一本化せず、別版・別Genesisへ代替しません。由来の省略IDは`unspecified`とし、origins未指定（`origins: unspecified`）と明示空（`origins: 0`）を区別します。表示順は署名中の集合順です。本文・metadataは出力せず、参照先の取得・依存評価・pin/公開判定は行いません。

`startup_state`は領域の診断であり、この表示の成功はGenesis/親/由来の外部照合、全祖先有効性、本文保持、評価確定、公開・復旧完了を意味しません。起動cursorを進めず、writer/finishや手動待ち解除を行いません。既存openが保持本文の欠損等を検出した場合は停止印・履歴を記録し、保全します。SQLiteのWAL/SHM等のI/Oはあり得るため、全fileの物理的不変は保証しません。

引数不正は接触前に終了2、未保持・三ID不一致・領域検査/予算/排他の失敗・出力失敗は終了1です。部分結果を成功にせず、稼働中IPC、直接保存、自動修復・再試行、残存物整理へ切り替えません。正常領域と既に手動待ちの領域を確認できますが、表示成功で停止印は解除されません。全保存版・分岐の確認は次の`document history`を使います。

保存範囲の全Revisionと親子宣言・同世代の管理用評価は、KnowledgeとGenesisを明示して確認します。鍵・パスフレーズ・制御端末は不要です。

```sh
./target/release/lngnb document history --data-dir /path/to/existing-data --knowledge-id KNOWLEDGE_ID --genesis-id GENESIS_ID
```

同じ排他/read transactionで共通の保存履歴・評価処理を使い、生Revision ID順に全保存版を表示します。各版の署名鍵、親と参照先の直接対応、scope内でそのIDを親と宣言する子、由来、`record_validation`と理由/関係ID、本文状態と理由を表示します。本文・metadataは出力しません。由来の三形・未指定/空・署名中の集合順を保持し、省略IDは`unspecified`です。`declared_root/merge/branch/tip`は親なし・複数親・複数の宣言上の子・宣言上の子なしを表し、別鍵の宣言も消しません。直接対応は二版の対応だけで、全祖先有効性ではありません。

`valid/pending/invalid`は対象Genesisを仮定した、その世代の非永続管理用診断です。保存先端やvalidだけへ絞らず、世界の完全履歴、評価済み現在候補、公開候補とは呼びません。validも本文保持・pin・公開・復旧完了を保証しません。由来は親履歴・承認・必須依存ではありません。`assessment_committed: false`は新しい評価や根拠を永続確定していないことを示し、`assessment_storage_fault`は評価器が観測した保存障害で全領域健全性の証明ではありません。既知不正の根拠不足もpending/理由を保ったまま診断します。

既存openの検査/予算を省略せず、一覧と評価は別々の全保存走査です。既定は一覧10,000 Record/64 MiB、選択親+由来100,000、一覧SQL callback100,000/60秒。評価も10,000 Record/64 MiB、親辺100,000、本文hash64 MiB。両段階は合計60秒を共有します。さらに出力準備は32 MiB/60秒で制限し、準備完了後に出力します。これらは非保存の操作予算で、保存4設定を追加/変更しません。OS I/O、一件の署名/hash、commit、標準出力の強制中断保証ではありません。

空scopeは`revisions: 0`で成功し、別Genesis/版へ代替しません。pending/invalid/保存障害や手動待ちでも診断を表示できますが、成功は正常停止・健全性・復旧完了を意味しません。引数不正は領域へ接触前に終了2、領域検査・排他・予算・読取り・出力の失敗は終了1。読取り/出力準備失敗では部分結果を出さず、出力途中のI/O失敗は診断と区別して失敗します。出力まで同じ排他を保持し、稼働中IPCへ切り替えません。参照取得、writer/finish、永続評価、起動cursor進行、手動待ち解除は行いません。既存openの異常検出による停止印/履歴とWAL/SHM等のI/Oはあり、全fileの物理的不変は保証しません。

手動確認待ちの保存領域で、根拠復旧の再検査と管理者の確認内容だけを記録する操作は次のとおりです。まず`data status`の`diagnostic_generation`と対象領域を確認し、その世代・復旧内容・まだ確認できていない事項をすべて明示します。

```sh
./target/release/lngnb data recovery-confirm --data-dir /path/to/existing-data --expect-generation N --restored '真正本文を復元しIDを照合' --unconfirmed '公開設定・未確定制限は未確認'
```

停止中の所有者/root専用領域と同じ排他・既存open検査を使い、現在世代の一致と手動待ちを要求します。確認文はそれぞれUTF-8で1〜4096 bytes、空白のみ・NULは拒否します。CLIは申告文を出力しませんが、確認履歴へ原文を保存します。操作者の実効UID・時点・規則版も既存履歴へ記録します。期待世代は非負の十進整数（先頭ゼロ・符号・空白なし）です。引数不正は領域接触前に終了2。古い世代・正常領域・未完了起動検査・保存異常・予算/SQL失敗は確認成功にせず終了1です。

一次Recordと参照本文を既存APIで再検査し、既知不正の各根拠が真正本文/実長と一致した場合だけ、確認履歴と派生評価のdirty化を同じFULL transactionで記録します。既定の領域検査は10,000 Record/64 MiB・10,000 Blob/64 MiB、根拠確認は10,000 Record/64 MiB・100,000親辺・本文hash64 MiB/60秒です。既存SQL検査予算も維持します。保存済みhash来歴への代替・検査省略・自動取込み/削除・修復・IPC切替はありません。OS I/Oや一件の署名/hash・commitの強制中断を保証せず、非保存の予算を保存4設定へ追加しません。

出力の`source_generation`・`recorded_generation`は確認対象と確認記録の世代です。commit後に既存APIが排他を解放するため、出力時の現在世代や独立した再開資格とは呼びません。`checked_evidence`は既知不正の根拠起点数で、0件も全体健全性の証明ではありません。参照外本文・孤立実体・staging・公開設定・未確定制限の全確認、親評価完了・起動完了・復旧完了を意味しません。未確認事項を解消済みと推測せず、既知不正の記録や署名済み一次データを変更しません。

開始履歴を先に確定するため、途中失敗でも世代が進み、開始履歴や確認が保存済みの場合があります。停止印とデータを保全し、古い期待世代で自動再試行しません。記録後の出力失敗は別の診断で終了1とし、記録を取り消したとは表示しません。成功・失敗・通常再起動のいずれでも手動待ちを維持します。writer/finish・明示再開・正常停止・公開資格への接続は行っていません。根拠確認の記録とローカル保存の明示再開は別操作です。

根拠復旧確認後にローカル保存を明示再開する場合は、確認結果の`source_generation`・`recorded_generation`・`checked_evidence`をすべて指定します。未確定だった制限を確認/再適用し、残る障害がないと判断した理由を原文で指定してください。

```sh
./target/release/lngnb data resume-local --data-dir /path/to/existing-data --source-generation SOURCE_GENERATION --review-generation RECORDED_GENERATION --checked-evidence CHECKED_EVIDENCE --confirm-restrictions-reapplied --confirmation '未確定制限を確認/再適用済み。現在の保存範囲に未解決障害なしと判断した理由'
```
