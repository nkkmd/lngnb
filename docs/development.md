この文書は、ビルド・試験の再現手順と内部APIの実装範囲を扱います。現在利用できるCLIは[ローカル操作](local-operations.md)と[管理受理側](admin.md)、工程と未完了事項は[実装計画書の現在地](implementation-plan.md#11-現在地と次の作業)を参照してください。

## ビルドと通常検証

現在のビルド確認対象はLinux x86_64（Ubuntu 24.04）です。RustupとCリンカー（Ubuntuでは`build-essential`）を用意し、取得したリポジトリ内で実行します。Rust 1.85.0・edition 2024を採用し、ツールチェーンと構成を固定しています。依存版はCargo.tomlとCargo.lockで固定しています。初回の依存取得にはネット接続が必要です。独立照合試験にはPython 3.12とvenvを用います（Ubuntuでは`python3-venv`）。取得後のRustビルド・試験はofflineで実行します。

```sh
git clone https://github.com/nkkmd/lngnb.git
cd lngnb
rustup toolchain install 1.85.0 --profile minimal --component rustfmt --component clippy
cargo fetch --locked
python3 -m venv /tmp/lngnb-reference
/tmp/lngnb-reference/bin/pip install -r tests/requirements.txt
export LNGNB_REFERENCE_PYTHON=/tmp/lngnb-reference/bin/python
cargo fmt --all -- --check
cargo clippy --locked --offline --all-targets -- -D warnings
cargo test --locked --offline --all-targets
cargo build --locked --offline --release
./target/release/lngnb --help
./target/release/lngnb --version
./target/release/lngnb config show
./target/release/lngnb config show --data-dir /path/to/data
```

実行時データや秘密情報はリポジトリ外で管理してください。正式な保存保証・性能評価の対象条件は仕様書に従い、ビルド成功と区別します。WSL2等の対応は未判定です。

## CIと専用ext4検証

自動検査は[CI定義](../.github/workflows/ci.yml)にあります。通常検査の後、[専用ext4スクリプト](../tests/qualify-ext4.sh)で使い捨て96 MiB loop ext4上の必須試験と既存回帰を実行します。通常検査で専用環境待ちになる試験を、未実行のまま合格にはしません。別枠の実行件数や再実行を通常件数へ重複加算しません。

専用検証はLinuxのloop mount、`mkfs.ext4`、非対話sudo等を必要とします。手順・前提はスクリプトを確認し、実デバイスや利用中の保存領域へ置き換えないでください。環境不足やEPERMは未実行・失敗として記録し、権限・製品条件・検査を緩めません。実ENOSPC、I/Oフック、process killの結果を、実デバイスEIOや電源断相当の合格へ読み替えません。

試験の対象commit・環境・設定・実測時間・成否と未実行事項を分けて記録します。正式性能・障害試験の条件と証拠保全は[計画書§6](implementation-plan.md#6-実装ゲートと試験方針)と仕様書§18・付録A12/A15が基準です。コードのビルド成功、対象回帰の成功、工程完了、G1〜G5合格、初期版完成は別々に判定します。

## 保存基盤の内部範囲と制限

局所検査の成功は、親履歴の検査完了・pin採用・公開許可を意味しません。保存機能は内部基盤と接続済みCLIの試験対象であり、公開リレーを含む製品全体の適合を意味しません。Blobの起動時照合では、不完全・孤立・破損・欠損を確認待ちにし、自動削除や公開を行いません。保存RecordとBlobの起動検査は途中から再開でき、未完了の間は通常の書込みへ進めません。起動検査から親評価までを段階的につなぐ内部経路でも、全段階の処理終了前にwriterを返さず、開始時の手動確認待ちを維持します。

管理用の親評価では、Record入力の収集・署名検査、参照本文Blobのファイル単位のhash検査、既定32 Recordずつの判定を分割して再開できます。検査来歴と現在の入力を照合し、完了した入力検査を再利用します。参照一覧・依存情報全体の読込みと順序構築、最後の評価確定には、引き続き集合全体の予算が必要です。詳しい境界は[実装計画書の§5.12〜5.13](implementation-plan.md)に示します。

収集完了・評価の処理終了・依存不足の解消は別々に判定します。不正根拠を再検査できない場合は保留とし、修復後も手動確認待ちを自動解除しません。根拠復旧の再検査と管理者確認を記録する内部機能を追加しています。その成功だけでは再開せず、別の明示操作と現在のデータ・再開台帳の検査を経て、ローカル保存の書込みだけを再開できます。一般配信の再開とは別です。結果はその世代の管理用診断であり、pin・公開資格を付与しません。根拠復旧の確認記録は`data recovery-confirm`、保存範囲の一覧は`document history`へ接続しています。ローカル保存の明示再開は`data resume-local`へ接続しています。同期通信は未実装です。

Blobの明示保持・本文参照・既知不正根拠に加え、期限付き内部仮保存の台帳と保護根拠の診断を追加しています。削除予定の記録・保持変更による取消しに加え、未参照・期限終了の本文を再検査して整理し、中断時に明示復旧する内部経路を追加しています。過去の約束と履歴は保全します。HTTP受付票・公開制御・バックアップとの整理結合は未実装です。

## 鍵管理の内部APIと未接続範囲

ここからは内部APIの説明です。CLIの存在や通常変更許可を意味しません。最新の工程区分は[計画書§11](implementation-plan.md#11-現在地と次の作業)、各契約・受入はリンク先の節を参照してください。

### 初期停止と履歴導入

残存暗号文と指定保全先の完全bytes・期待鍵を再照合する非破壊内部APIを追加しています（[計画書§5.93](implementation-plan.md#593-工程⑤残存暗号文と明示保全先の非破壊再照合)）。成功は保存確定・削除資格・停止解除を意味しません。 A案の明示導入・初期停止を保存する内部APIも追加しています（[計画書§5.95](implementation-plan.md#595-工程⑤a案の明示導入初期停止の内部基盤)）。自動導入や解除・整理・置換・CLI接続は行いません。 完全markerと期待area_idを照合し、初期停止だけを明示復旧する内部APIも追加しています（[計画書§5.96](implementation-plan.md#596-工程⑤完全markerから初期停止への明示復旧)）。不完全な既存fileは補完せず、停止を維持します。 履歴付き初回Heldの有界検査・明示導入も内部APIへ接続しています（[計画書§5.98](implementation-plan.md#598-工程⑤履歴付き初回heldの有界検査と明示導入)）。履歴欠損や導入一時名を空履歴へ戻さず、初期専用復旧による迂回も拒否します。完全v2と明示した初回履歴が一致する場合に限り、導入中断を明示復旧する内部APIも追加しています（[計画書§5.99](implementation-plan.md#599-工程⑤履歴導入中断の限定的な明示復旧)）。欠損履歴は生成せず、成功後も停止を維持します。通常変更再開・CLIは未接続です。

### 整理履歴の検査と開始

鍵履歴の整理開始/完了eventを厳密に検査し、初回rootと全履歴からHeld/Activeを導く読取り診断の内部APIも追加しています（[計画書§5.101](implementation-plan.md#5101-工程⑤後続整理eventの厳密codecと全履歴の読取り診断)）。この読取り診断は認証・保存確定・削除資格・通常変更許可を与えず、追記や整理を実行しません。

元/保全先の保持fd・認証・今回のfsync確認から、全履歴を残した一件の整理開始追記までの内部APIを追加しています（[計画書§5.102](implementation-plan.md#5102-工程⑤保持fd今回の保存確認と一対象の整理開始追記)）。この開始APIは成功後もActiveとして停止を維持し、対象鍵の削除・停止解除を行いません。

控えた旧/新hash・操作IDと、完全な既存snapshot・両暗号文を照合して整理開始の追記中断だけを明示復旧する内部APIも追加しています（[計画書§5.103](implementation-plan.md#5103-工程⑤整理開始の追記中断を限定的に明示復旧する)）。今回の保存確認後もActive/停止を維持し、不完全な候補は補完・自動採用しません。この開始復旧APIは対象鍵を整理せず、停止を維持します。

### 完了追記と一対象の整理

対象をunlinkせず、現在の不在と認証した保全先・開始履歴を再確認して不在完了を追記する内部APIと、その完了追記中断の明示復旧を追加しています（[計画書§5.105](implementation-plan.md#5105-工程⑤対象をunlinkしない不在完了と完了追記の明示復旧)）。既存の完全な完了候補だけを復旧し、不完全候補は補完しません。成功後もHeld・停止を維持し、過去のunlink/fsync成功を推定しません。この不在APIは対象鍵を削除せず、停止解除・通常更新・CLIは未接続です。

保存済みの開始意思に対応する一対象だけを認証・保全照合し、保持fdと今回の保存確認を経て明示整理する内部APIを追加しています（[計画書§5.106](implementation-plan.md#5106-工程⑤一対象の保持fdに束縛した物理整理と正常完了)）。unlink後も元fdの属性・完全暗号文と対象不在を検査し、元directoryの保存確認後だけ正常完了を準備・追記します。中断は不在完了または既存完全候補の明示復旧へ進み、成功後もHeld・通常変更停止を維持します。鍵の完全消去・失効や停止解除を意味せず、CLIは未接続です。

### 論理Ready・再開意思の記録と追記復旧

明示再開eventの厳密codecと、全整理完了参照・全履歴rootから論理Readyを導く検査を追加しています（[計画書§5.109](implementation-plan.md#5109-工程⑤明示再開eventの厳密codecと論理readyの検査)）。Readyも再開の保存確定や認証・通常変更許可ではありません。読取り診断は記録したguardが現存し全identityが一致する範囲だけを扱い、不在を解除成功として受理しません。この読取り診断は追記を行いません。

全整理完了に対応する保全先と現在鍵を保持・認証し、今回のfile/directory fsync後に再開意思一件だけを記録する内部APIも追加しています（[計画書§5.110](implementation-plan.md#5110-工程⑤全保全の資格保持と再開意思一件の追記)）。共有/別領域の保全先をすべて再検査し、漏れ・不一致・資源不足は追記前に拒否します。成功後もguardと通常変更停止を維持します。完全な既存snapshotの三配置だけを扱う追記中断の明示復旧も追加しています（[計画書§5.111](implementation-plan.md#5111-工程⑤guardを保持する再開意思の追記中断の明示復旧)）。復旧も全保全を再認証・今回fsyncし、guardと停止を維持します。

記録guardの解除は別の内部APIを明示的に呼び出します（[計画書§5.112](implementation-plan.md#5112-工程⑤記録guardの明示解除と中断後の保存確認)）。固定Readyと控え、追記一時名の不在、現在鍵と全保全先を確認します。記録guardの解除または正確不在について今回の保存確認を返します。通常鍵更新には別の準備が必要です。

最初のパスフレーズ変更は内部APIで非破壊準備・開始追記・新暗号文の一時保存・準備追記まで扱います（[計画書§5.117](implementation-plan.md#5117-工程⑤新暗号文の一時保存と準備追記)）。準備追記の明示復旧は、控えと完全な履歴候補、記録済みの新暗号文を再認証します。旧通常名、保全先、guardを保持します。記録済み両暗号文の交換と交換後の明示確認は内部APIで扱います（[計画書§5.118](implementation-plan.md#5118-工程⑤鍵の交換と交換中断の明示確認)）。交換後も旧暗号文を一時名で保持します。旧暗号文の整理、完了と解除、CLIへの接続は後続です。
