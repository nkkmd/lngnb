# lngnb 初期版実装計画書

- **文書状態：** 正式採用
- **計画版：** 1.0.0
- **作成日・更新日：** 2026-10-24
- **基準仕様：** LNGNB-SPEC-001／[仕様設計書 v1.0.0](specification-v1.0.0.md)
- **配置先：** `docs/implementation-plan.md`
- **対象：** 初期プロファイルに基づく実装、検証、初期公開の準備

## 1. 目的と位置付け

lngnbを、軽量でシンプルなインターネット上の分散図書館として実装する。

本計画は、仕様設計書 v1.0.0で確定した機能と受入条件を、依存関係に沿って実装・検証するための手順を定める。規範の詳細は仕様書を参照し、本計画で重複定義しない。

仕様書と本計画に不一致がある場合は、仕様書を基準として計画を修正する。仕様自体に矛盾や実装上の問題を発見した場合は、理由・影響・対応案を整理して所有者の判断を確認する。実装都合で規範を暗黙に変更しない。

仕様書のv1.0.0、本計画の版、ソフトウェアのリリース版は別に管理する。文書の確定は製品試験の合格を意味しない。

## 2. 初期版の完成条件

次の三つの利用場面を成立させ、仕様書§18・§19および付録の受入条件を満たす。

1. **一台で資料を利用できる。**  
   資料の作成・登録・公開、検索・閲覧、固定版の引用、改訂履歴の参照ができる。

2. **必要な資料を別のリレーへ引き継げる。**  
   管理者が選んだKnowledgeを独立して検証・保持し、元リレー停止後も保持先で同じ固定版を参照できる。

3. **バックアップから復元できる。**  
   資料・不変ID・履歴・信頼設定・公開設定を保全し、検査と管理者の確認を経て配信を再開できる。

機能動作に加え、非公開情報の保護、保存の耐障害性、通常操作の分かりやすさ、正式な軽量性基準を確認する。

必須試験が未実行、環境不足で保留、または不合格の場合は、初期版完成と判定しない。完成判定と、リポジトリ公開・ソフトウェアのリリースは区別する。

## 3. 実装の基本方針

### 3.1 小さな単位で積み上げる

形式・ID・署名を先に固め、その上に保存、ローカル操作、公開、閲覧、同期、復元を実装する。

工程は必要に応じて複数の小さなPRに分ける。工程全体の完成まで巨大な差分を保持せず、検証可能な単位でmainへ統合する。未完成部分は未完成と明示し、安全条件を省略した状態で外部へ露出させない。

### 3.2 初期必須の範囲を守る

初期Record種別はGenesisとRevisionとする。

高度な権限管理、同一Knowledgeの鍵交代・復旧、管理Web画面、全文検索、連邦検索など、仕様書で後段に分けられた機能を先行実装しない。

初めは一つのRustパッケージを内部モジュールで分ける。将来拡張だけを目的とした抽象化や複数クレートへの分割を避け、具体的な必要が生じた場合に構成を見直す。

### 3.3 保存・安全性・処理上限を同時に実装する

不変データ、検証状態、信頼起点、公開許可、本文取得状態、完全性、鮮度を混同しない。

保存順序、排他、起動・終了状態、重要履歴、処理予算、公開停止時の遮断は、対応機能と同時に実装する。

共通基盤の試験が完了していても、後続工程で追加した設定や操作について、保存失敗・起動・再評価・公開制御との結合試験を行う。

### 3.4 実装内の自己照合だけに依存しない

暗号方式やTLS自体を独自実装しない。採用ライブラリが仕様の厳格な受理条件を満たすことを、製品側で確認する。

仕様の固定計算例との一致に加え、暗号・符号化等の重要部分は、製品と異なるライブラリや小規模な参照検査手段でも照合する。第二の完全なlngnbリレー実装の開発は要求しない。

同じ製品による二リレー試験と、異なる実装との相互運用確認を区別し、実際に確認した範囲を記録する。

## 4. 実装工程

以下は着手順序である。各工程の完了は、その範囲の実装と検証の完了を示す。G1〜G5の最終合格とは区別する。

### 工程① 要件と検証の対応整理

**実施内容**

- 規範要件を担当工程・実装対象・試験へ対応付ける。
- §18.1、§20の初期対象、付録A15、G1〜G5との対応を確認する。
- 付録A15の試験例だけで全規範要件を網羅したと扱わない。
- 独立照合、障害注入、性能測定に必要な環境を確認する。
- Linuxの正式対象条件と、別途評価が必要な環境を区別する。
- 本計画の対応表を、工程着手に必要な粒度まで具体化する。

**完了条件**

初期必須要件に担当工程と確認方法がある。試験環境の不足は、解消方法・確認時期とともに明示されている。

環境不足を試験免除や合格へ読み替えない。工程①の完了時に全試験環境の稼働までは要求しないが、該当試験の実施前に必要条件を満たす。

### 工程② Rustの最小構成とCI

**実施内容**

- Rustパッケージ、最小CLI、設定・エラー処理の基礎を作る。
- 必要な依存ライブラリを選び、採用版とビルド条件を固定する。
- 書式、静的検査、単体試験、ビルドをCIで確認する。
- 実行時データ、秘密情報、生成物をGit管理対象から除外する。

**完了条件**

新規取得した環境から、文書に沿ってビルドと基本試験を再現できる。未実装の操作を成功と表示しない。

### 工程③ Record・CBOR・ID・署名

**実施内容**

- 決定的CBOR、厳密スキーマ、型・構造・サイズ上限を実装する。
- domain分離、ハッシュ、各種IDと外部表記を実装する。
- Genesis・Revisionの署名と発行鍵の整合を検査する。
- 未対応プロファイル・種別を区別し、既知形式へ読み替えない。
- 固定計算例、不正入力、境界条件を検証する。
- 重要部分を独立した検査手段でも照合する。

**完了条件**

付録A13のbytes・署名・IDが一致し、不正な符号化・署名・ID表記を拒否できる。

製品内で生成して読み戻す試験に加え、固定値と独立した照合によって誤りを検出できる。照合対象と未確認範囲が記録されている。

### 工程④ 保存基盤と状態の再評価

**実施内容**

- SQLiteと内容アドレスBlob保存を実装する。
- ファイル・DBの確定順、排他、容量予約、処理上限を実装する。
- 設定・判定・重要履歴・世代を整合して更新する共通基盤を作る。
- 起動検査、稼働中印、正常停止印、手動確認待ちを実装する。
- 親依存、分岐・複数親、本文ハッシュと宣言長、子孫の再評価を扱う。
- 判定根拠と再開情報を保全する。
- 仮保存・保持・整理の競合を扱う基礎を作る。
- 保存実装ID・保存スキーマ版を管理し、非対応版を推測で開かない。

**完了条件**

同一入力の再処理が不変データを壊さず、依存不足・既知不正・本文不足を区別できる。実装済み範囲の保存失敗・異常終了試験に合格する。

仕様が定める同じ条件から、到着順によらず同じ意味上の検査結果・候補集合を得られる。

この段階では保存と状態更新の共通基盤を完成させる。工程⑥で追加するpin・公開操作等の結合試験は、当該工程で行う。

### 工程⑤ 鍵管理とローカル操作の基盤

**実施内容**

- データ領域の明示的な初期化と、管理状態の確認を実装する。
- 暗号化鍵ファイルの作成・読込み・更新を実装する。
- 資料の作成・署名・改訂・派生のCLIを実装する。
- 稼働中は保護されたUnix domain socketを通し、停止中は同じ排他・保存規則を使う管理操作の共通基盤を作る。
- 異常状態の確認と明示再開に必要な管理操作を実装する。
- 発行秘密鍵をリレーDB・公開HTTP・管理IPCへ渡さない。
- 鍵の保全、紛失・漏洩時の限界と新Knowledgeへの移行を案内する。

**完了条件**

ローカルで資料と改訂を作成し、保存版・分岐・由来を確認できる。

付録A14の固定例と鍵関連の異常系を検証し、失敗時に元の正常な鍵ファイルを破壊しない。管理操作の成功で、無関係な手動確認待ちを解除しない。

pin・公開・投稿・同期等の具体的な管理コマンドは、各機能の実装工程でこの基盤に接続する。

### 工程⑥ 公開制御・投稿・HTTP(S) API

**実施内容**

- pinの採用・変更・解除、隔離、通常公開と未確認公開を実装する。
- 手動公開を既定とし、明示設定による後続版の自動公開を実装する。
- Open／Restricted投稿と、トークンの発行・失効・再発行・Knowledge範囲制限を実装する。
- 仮保存、受付状態照会、保持への移行と整理を実装する。
- Record・Blob・状態・一覧等のAPIと内蔵HTTPSを実装する。
- 一覧の固定、ページング、公開縮小時のtoken無効化を実装する。
- 公開停止の先行遮断、共有Blobの公開根拠、非開示の応答・集計を実装する。
- Origin・CORS、Host、プロキシ、証明書失敗時の動作を確認する。
- 具体的な管理操作をCLIへ接続する。

**完了条件**

初期設定がループバック待受・Restrictedとなり、外部公開とTLSを管理者が明示設定できる。

公開許可と検証条件が揃った対象だけを配信し、固定ID、一覧、状態応答、共有Blob等から非公開情報を漏らさない。公開停止の保存失敗でも遮断を維持する。

追加した設定・操作について、保存・起動・履歴・再評価との結合試験を完了する。

### 工程⑦ 検索・閲覧・固定引用

**実施内容**

- Catalogと仕様どおりのメタデータ検索を実装する。
- 現在候補、履歴、分岐、本文取得状態を表示する。
- 固定版の引用出力と、Web・CLIからの固定ID指定を実装する。
- プレーンテキストの安全表示と、その他の媒体の安全なダウンロードを実装する。
- 索引の更新・再構築と公開制御の整合を検証する。

**完了条件**

一台で最初の利用場面を完了できる。複数候補を勝手に一つへ選ばず、未確認資料を通常の候補一覧へ混在させない。

索引が古くても公開停止を迂回できない。固定IDの指定で別版への置換や自動Pullを行わない。

### 工程⑧ リレー間の選択的複製

**実施内容**

- 管理者による同期元登録とKnowledge単位のPullを実装する。
- 接続先の分類、DNS解決後の接続固定、TLS検証を実装する。
- 目録／本文モード、一覧照合、取得、独立検証を実装する。
- 工程⑥の一覧提供側と取得側を組み合わせて検証する。
- ジョブ予算、キュー、中断・再開、token失効、上限付き再試行を扱う。
- 完全性・鮮度・照合範囲と時計異常を扱う。
- 明示有効化した場合だけ実行する定期同期を実装する。

**完了条件**

二台間で必要な資料を引き継ぎ、元リレー停止後も保持先で同じ固定版を参照できる。

相手の判定を無条件に信頼せず、部分取得・転送失敗・予算到達を完全な同期成功として扱わない。完了済み一覧と未完了一覧を区別して再開できる。

### 工程⑨ バックアップ・復元・運用検証

**実施内容**

- 一貫したDBコピー点と対象Blobの保護に基づくバックアップを実装する。
- manifest・COMPLETEの検査と、別の空データ領域への復元を実装する。
- 根拠、隔離資料、必要設定、再開情報を保全する。
- 復元後の再検査、索引再構築、新しいnamespace、手動再開を実装する。
- 復元された一覧・token・取得進捗・観測時刻を検証する。
- 保持・整理・退避、容量不足、重要履歴の保存失敗を総合検証する。
- 対応するDB移行がある場合、移行前バックアップ、移行、失敗時の復帰を検証する。
- 異常時の状態確認から明示再開までをCLIで実施する。

**完了条件**

三つ目の利用場面を完了できる。不完全なバックアップを完成扱いせず、復元で過去の同期成功時刻や公開許可を捏造しない。

process kill、書込み失敗、容量不足、電源断相当を区別して検証する。電源断相当は適切な隔離環境で実施し、process killだけで代替しない。

### 工程⑩ 総合受入と初期公開準備

**実施内容**

- 公開候補コミットに対する要件・試験結果を整理する。
- G1〜G5、§18および関連付録の対象に不足がないか確認する。
- 正式な性能・操作性試験を実施する。
- 導入・通常運用・バックアップ・復元の手順を実機で確認する。
- リポジトリと履歴、配布物に秘密情報や不要な実行データがないか確認する。
- README等を実装状態・対応環境・既知の制約に合わせる。
- 最終結果を再確認できる形で保存する。

**完了条件**

必須要件と試験を充足し、未実行・不合格を残したまま完成と表示していない。公開対象、リリース版、試験結果、既知の制約が確認できる。

リポジトリの公開とリリースは、所有者の指示に基づいて実施する。

### 6.1 試験の組合せ

単体試験、結合試験、三利用場面の試験、障害試験、性能・操作性試験を組み合わせる。

正常系の成功だけでなく、不正入力や障害時に、不正な状態遷移・公開・データ破壊が起きないことを確認する。競合、到着順、再起動、再投稿による違いも対象とする。

### 6.2 軽量性の確認

正式条件は仕様書§18.2・付録A12を参照する。主要値は次のとおりである。

| 項目 | 正式な条件 |
|---|---|
| 環境 | Linux、1 vCPU相当、RAM 1 GiB、swapなし、ローカルSSD |
| データ | 1,000 Knowledge、10,000 Revision、本文合計1 GiB |
| 待機RSS | 128 MiB以下 |
| 通常閲覧・検索RSS | 256 MiB以下 |
| 同期・再索引・起動検査RSS | 512 MiB以下、cgroup全体1 GiBでOOMなし |
| 応答 | 同時5利用、ウォーム時の検索・固定参照メタデータが各p95 500 ms以下 |

関連機能の成立後に予備測定し、大きな問題を早期に発見する。予備測定を正式合格へ読み替えない。

正式試験では、付録A12のfixture、反復、負荷、TLS条件、計測方法、判定手順を守る。性能のために検査・耐久性・公開制御を弱めない。

### 6.3 試験結果の保存と再利用

最終判定に使う結果には、少なくとも次を含める。

- 対象コミット、ビルド条件、成果物の識別情報
- 試験環境、依存ライブラリ版、実際の設定
- 入力データの生成方法とmanifestのハッシュ
- 実行手順、期待結果、実結果
- 未実行・不合格・保留の項目
- 性能の生データと障害試験の記録

大容量データや生ログはリポジトリ外に保持し、リポジトリには要約と参照先を残す。保存期限のあるCI成果物だけを最終合格の唯一の根拠にしない。最終判定前に、必要な証拠が参照・取得できることを確認する。

試験後の変更は影響範囲を評価し、必要な試験を再実行する。過去の結果を引き継ぐ場合は、元の対象コミットと、変更が結果へ影響しない理由を記録する。

文書だけの修正など、実行結果に影響しない変更にまで、一律に全性能試験の再実行を要求しない。判断できない場合は該当試験を再実行する。

## 7. 保存形式の版管理と移行

保存実装ID・保存スキーマ版と、ネットワークのプロファイル版を区別する。ネットワーク互換性からDB復元互換性を推測しない。

初期開発中の試験用DBは、引継ぎ可能な版と再作成が必要な版を明示する。すべての試作版からの移行機能は要求しないが、非対応DBを黙って初期化・上書きしない。

移行を提供する場合は、対応元・対応先、移行前バックアップ、成功確認、失敗時の復帰手順を定めて検証する。未知・非対応の保存形式は拒否する。

保存済みデータを破棄する操作は、通常の起動や更新の副作用として行わない。

## 8. 変更とmain統合の手順

1. 対象仕様、変更範囲、確認方法を明らかにする。
2. 作業ブランチで実装と必要な試験を追加する。
3. 関連試験とCIを実行する。
4. 差分、仕様との一致、既存機能への影響、文書の整合を確認する。
5. PRへ目的・動作・検証結果・未完了範囲を記録する。
6. 必要な確認を満たした変更をmainへ統合する。
7. 統合内容と試験対象の対応を確認し、対応表を更新する。

統合時に競合解消等で実装差分が変わった場合は、変わった範囲を再検証する。

実装途中のmain統合は、初期版完成や一般公開を意味しない。検証を省略して成功を返す代替処理を、完成機能として組み込まない。

## 9. 判断が必要な場合

以下の場合は、理由・影響・推奨案を整理して所有者へ確認する。

- 初期機能の範囲、保証、正式な合格条件を変更する場合
- Record、署名、ID、API等の外部形式や互換性へ影響する場合
- 仕様の矛盾や複数の解釈によって外部動作が変わる場合
- 新たな外部サービス、費用、本番環境への影響が必要になる場合
- リポジトリ公開やリリースを実施する場合

内部の関数名、テーブル構成、CLI名、画面配置、仕様を満たす依存ライブラリの選択等は、実装裁量で進める。

既に判断済みの事項を、同じ条件で繰り返し確認しない。一部の判断が未確定の場合も、それに依存しない作業は継続する。

## 10. リポジトリと文書の管理

- READMEは概要・現在地・導入情報への入口に保つ。
- 仕様書は規範、本計画は工程・完了条件・要件と試験の対応を扱う。
- 個別の経過はIssue・PRへ記録し、日付ごとの進捗文書を増やさない。
- ソース、試験、必要な小規模固定データ、再現用スクリプトをGit管理する。
- 大容量の生成データ、実行時DB、秘密鍵、トークン、不要なログはコミットしない。
- 雛形、空ディレクトリ、用途のない設定ファイルを追加しない。
- 文書は必要になった時点で追加し、同じ内容の重複管理を避ける。

コードと仕様書を含む文書にはMIT Licenseを適用する。第三者の著作物や、lngnbで保存・配布する資料の利用条件は別に扱う。
